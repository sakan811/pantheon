# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Themis: a mastering check suite in one plugin (VST3 + AU, Standalone) built on JUCE 8.0.6, in the style of iZotope Tonal Balance Control: tonal balance against a reference curve, device translation, mono fold / phase cancellation, stereo correlation, low-end dynamics (crest), clipping / true peak, bass fundamental, energy over time (bands, mid/side, left/right). Targets FL Studio on macOS (universal arm64 + x86_64, macOS 11+). See [README.md](README.md) for the feature list and the "verified / not verified" table.

## Core principles (apply to every change)

- **Clean and transparent: monitoring and decisions only.** Themis never processes the audio: no EQ, dynamics, limiter, gain or dither, bit-exact pass-through, zero latency. A feature belongs here if it helps the user *judge* a master (a measurement, a verdict, a graph, advice); it does not belong if it *processes* the signal. The one exception is the Solo / Mute audition ([Audition.h](core/include/themis/Audition.h)), which lets the user *listen* to what a check flags: it changes the output only while a button is pressed, is bit-exact when idle, is not saved with the session (atomics in the processor, not APVTS), is skipped when `isNonRealtime()`, and runs *after* every measurement so the analysis always sees the input. Don't add other output-altering features, and don't let anything but the audition write to the buffer. The full mastering chain left in `core/` is not used by the plugin and must stay that way.
- **The plugin tells the user what to do, from measurements only.** [MasterAdvisor.h](core/include/themis/MasterAdvisor.h) is the one place that turns measurements into advice (`advise()`, a pure function on `MasterInputs`, tested without a UI). A new check adds its own item there, with the amount and place computed from a measurement, a tooltip-length *why*, a `hear` audition hint where there is something to listen to, and a test; it reuses the verdict functions that already own the limits (`translation::`, `history::`, `lowcrest::`) instead of redefining thresholds. Never invent a number: if a recommended amount is not derived from a measurement, leave it out of the text.
- **Everything a mastering check needs, in one place.** New checks should read from the shared analysis (one FFT, one grid) and surface as a readout, a graph or an overlay in the existing editor, with a tooltip explaining the numbers. Say plainly in the UI/README when a limit is a rule of thumb rather than measured data.
- **Always update the screenshot after any update.** After any change that touches the UI or what it displays, regenerate [docs/screenshot.png](docs/screenshot.png) and [docs/graphs.png](docs/graphs.png) (every tab of the two history graphs) with the `ThemisSmoke` command below (pass both paths) and look at them. If a feature has no visible trace in the demo programme (`runDemoProgramme` in [tests/plugin_smoke.cpp](tests/plugin_smoke.cpp)), extend the programme so it does, and keep the README caption true to what the picture shows.
- **DRY.** Look for the existing helper before writing logic: [Common.h](core/include/themis/Common.h), `translation::classify`, `kEnergyRanges`, `FrameStats::forEachField`, the `history::` verdicts ([HistoryChecks.h](core/include/themis/HistoryChecks.h), the one place that decides what a graph's verdict line says), `ui::signedDb`/`ui::hzText`, `ui::MeterCell`, `ui::HistoryPanel`, `colours::forLevel`, the test helpers (`analyseWhole`, `runBlocks`). If a second copy of a constant, threshold, formula, label or drawing routine appears, move it to the one place that owns it and use it from both.

## Commands

```bash
make test                                   # build + run all DSP tests (g++/clang++ only, no JUCE, no network)
CXX=clang++ make test                       # override the compiler

# Full plugin (fetches JUCE via FetchContent, needs git + network on first configure)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target Themis_VST3 Themis_AU -j8   # Themis_AU is macOS only

# Headless JUCE smoke test (real processor + editor, no host/display); writes a UI screenshot
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DTHEMIS_BUILD_SMOKE=ON && cmake --build build --target ThemisSmoke
./build/ThemisSmoke_artefacts/Release/ThemisSmoke docs/screenshot.png docs/graphs.png   # the README images: regenerate after every UI-visible change
```

- On macOS the plugin build **copies the plugins into `~/Library/Audio/Plug-Ins/{VST3,Components}`** by default (`THEMIS_INSTALL_AFTER_BUILD`, default `${APPLE}`). Pass `-DTHEMIS_INSTALL_AFTER_BUILD=OFF` to avoid touching those folders. Apple Silicon needs an ad-hoc `codesign --force --deep --sign -` on the result (see README).
- Other CMake options: `THEMIS_BUILD_PLUGIN`, `THEMIS_BUILD_TESTS` (both default ON).
- There is no linter or formatter config in the repo. The Makefile compiles tests with `-Wall -Wextra -Wpedantic -Wconversion`; the plugin target uses JUCE's recommended warning flags and is kept warning-free in Themis' own sources.
- **Running a single test:** the test runner has no CLI filtering ([tests/test_main.cpp](tests/test_main.cpp) `main()` runs every `TEST(name)` registered). To iterate on one, temporarily comment out others or add an early filter; don't assume `--gtest_filter`-style flags exist. The tests use a tiny custom framework (`TEST`, `CHECK`, `CHECK_NEAR`), not Catch/GoogleTest.
- CI ([.github/workflows/build.yml](.github/workflows/build.yml)): `make test` on Linux, a universal macOS VST3 + AU build with `lipo`/`codesign`/`auval`, and a Linux VST3 compile check. Tagging `v*` publishes a release.

## Architecture

Two layers with a hard dependency direction: `plugin/` → `core/`, never the reverse.

**`core/include/themis/` — header-only, dependency-free C++17 DSP** (no JUCE types). The plugin only uses [Audition.h](core/include/themis/Audition.h), [LoudnessMonitor.h](core/include/themis/LoudnessMonitor.h), [MasterAdvisor.h](core/include/themis/MasterAdvisor.h) (all three below), [TonalAnalyzer.h](core/include/themis/TonalAnalyzer.h), [TargetCurve.h](core/include/themis/TargetCurve.h), [Translation.h](core/include/themis/Translation.h) (generic `DeviceProfile` responses + `analyseTranslation`: device loss vs the target, mono loss, with hand-authored traffic-light limits in `translation::`; pure functions, analysis only), [LowCrestMeter.h](core/include/themis/LowCrestMeter.h) (20–250 Hz crest factor; runs a few biquads on the audio thread, publishes via atomics), [ClipMeter.h](core/include/themis/ClipMeter.h) + [HistoryChecks.h](core/include/themis/HistoryChecks.h) (see below) and [StereoScope.h](core/include/themis/StereoScope.h) (vectorscope ring + smoothed L/R correlation, written by `push()` on the audio thread; fixed-size ring so readers never see a reallocation). The rest ([Engine.h](core/include/themis/Engine.h), EQ, compressor, limiter, loudness, EqFit…) is a full mastering chain that the plugin **no longer uses** but that is kept, with its tests, in `core/`.

- **One place for shared logic (keep it DRY):** [Common.h](core/include/themis/Common.h) owns the dB/power conversions (`dbToPower`, `powerToDb`, `kPowerFloor`), mid/side (`midOf`/`sideOf`), the averaging maths (`emaWeight` + `runningMeanWeight`, "cumulative mean until the EMA catches up") and `kDefaultAveragingSeconds`; `smoothBands` lives next to `normaliseAnchor` in TonalAnalyzer.h; `translation::classify`/`toleranceLevel` are the only traffic-light thresholds. Use these instead of re-deriving them inline. In the plugin, [Parameters.h](plugin/Source/Parameters.h) holds every choice table (`avgTimes`, `customTargetIndex()`, `deviceForChoice()`, defaults), and the display code shares fonts (`ui::font`), `colours::forLevel` and the meter geometry ([MeterCell.h](plugin/Source/MeterCell.h)).
- **Master plan ([MasterAdvisor.h](core/include/themis/MasterAdvisor.h)):** `advise (MasterInputs)` returns `Advice` items (`level`, `topic`, `headline` = what to change and by how much, `why`, `hear` = a `Switches` that auditions it), worst first (level, then `Topic` order), plus `checks` / `passed` and `measuring` (< `master::kMinSeconds` of audio: only clipping is judged, it is exact). `ThemisProcessor::masterInputs()` gathers everything on the message thread (spectrum, target, `analyseTranslation`, `analysePhase`, crest, `ClipTotals`, loudness, a copy of the history window) and `AdvicePanel` re-reads and re-advises twice a second. Tonal items come from `master::tonalRuns` (out-of-tolerance runs of ≥ 2 adjacent bands on the smoothed curve, the two with the largest excess), the move being the smallest one that lands inside the tolerance. The loudness target is the `loudnessTarget` parameter (`params::loudnessTargets`; append only, the index is saved); `master::kStreamingLufs` is the one -14 LUFS constant. Level / zone constants it shares with the readouts live with their owners (`lowcrest::` in LowCrestMeter.h, `BandGrid::usableMaxHz`), not in the view.
- **Loudness ([LoudnessMonitor.h](core/include/themis/LoudnessMonitor.h)):** wraps `LoudnessMeter` (Loudness.h, BS.1770 K-weighting + gating, histogram) for the audio thread and publishes integrated / short-term / loudest short-term LUFS and elapsed seconds through atomics; `requestReset` is applied by the next `process()` (same pattern as `LowCrestMeter`), `resetAnalyzer()` requests it, and `hasData()` is false for the first 3 s and while a reset is pending. The elapsed seconds are what the plan's `measuring` state counts.
- **Audition ([Audition.h](core/include/themis/Audition.h)):** `Switches` (solo / mute bit masks per `Source`: mid, side, left, right, then the four `kEnergyRanges`) → `resolve()` → `Audible` (solo silences the rest of its group, mute wins over solo, groups combine) → `Audition::process` on the audio thread: LR4 crossovers at the `kEnergyRanges` edges with all-pass compensation (ranges sum flat), then a 2×2 channel/mid-side matrix, all ramped over 10 ms. It returns early (buffer untouched) while `settledAtUnity && target.untouched()`. The switches travel in one `std::atomic<uint32_t>` (`pack` / `unpack`); `ThemisProcessor::processBlock` calls it *after* every meter and only when `!isNonRealtime()`. `AuditionPanel` mirrors the processor state (so `AdvicePanel`'s HEAR chips and the buttons stay in step); nothing about it goes into `getStateInformation`.
- **Phase, energy and fundamental (all fed by the same analyser frames, no extra FFT):** `analyseFrame` takes the *complex* mid and side spectra, so besides the tonal curve and mono fold it averages the per-band cross-spectrum (`foldCrossRe/Im`) and publishes `PhaseBands` (`readPhase`: correlation = (M−S)/(M+S), coherence, `arg(L R*)`, and a mid+side `levelDb` that exists even for a pure-side signal). [PhaseCancellation.h](core/include/themis/PhaseCancellation.h) `analysePhase` is a pure function on that: it flags bands with the mono-fold strip's own limits (`translation::kBandMonoWarnDb/BadDb`), takes the widest run of ≥ 2 bands, and fits `phase = -2πfτ` / `π - 2πfτ` to the coherent bands < 4 kHz to call polarity flip vs delay (notch = 1/(2τ)). Every frame also pushes a `FrameStats`: absolute mean-square dBFS of five `Signal`s (stereo = mid+side, mid, side, left, right) in each `kEnergyRanges` range plus a whole-spectrum column (`kAllRanges`), from the per-band mid/side/cross-spectrum energies (L/R power = M+S ± 2 Re(M S*)), scaled by 2/fftSize; `estimateFundamental` on the mid spectrum (see [Fundamental.h](core/include/themis/Fundamental.h)); and the peaks / clips of the audio since the previous frame (below). It goes into the fixed-size atomic ring [FrameHistory.h](core/include/themis/FrameHistory.h), which the UI graphs read (`ThemisProcessor::frameHistory()`). Energy/fundamental levels are deliberately *absolute*, unlike the tonal curve; digital-silence frames push `kHistoryFloorDb` (they still carry the clip window). Adding a field to `FrameStats` means adding it to `forEachField` and `kFields` only. `kEnergyRanges` is the single definition of LOW/LOW-MID/HIGH-MID/HIGH for both the readouts and the graph. The fundamental thresholds in `fundamental::` are tuned on synthetic tones only.
- **Clipping ([ClipMeter.h](core/include/themis/ClipMeter.h)):** owned by `TonalAnalyzer`, run by `push()` on the audio thread (a 4× `TruePeakDetector` per channel, ~0.6 % of a core at 48 kHz, no allocation). It reports sample peak, true peak, `over` samples (≥ 0 dBFS) and `clip` events = flat tops (≥ `kMinRun` equal samples ≥ −6 dBFS reached with a step ≥ `kEntryStep`; the entry step is what keeps a 16-bit-quantised loud bass sine from counting, see `clip_meter_does_not_mistake_a_quantised_bass_sine_for_clipping`). Cross-thread: window accumulators are atomics drained by `take()` in `analyseFrame` (so each history frame carries what happened since the previous one), totals since the reset are atomics read by `ClipTotals`; `requestReset` is applied by the next `push()` (the detector state belongs to the audio thread) and `totals().have` is false while it is pending. `prepareOffline` (learning from files) switches it off. `history::clip::level` is the one verdict (any clip/over bad; true peak > −1 dBTP warn, > 0 bad), used by the CLIPPING cell and the PEAKS tab.
- **History verdicts ([HistoryChecks.h](core/include/themis/HistoryChecks.h)):** pure functions on a window of `FrameStats` (`analyseSwing`, `analyseWidth` (mono loss, reusing the `translation::` mono-fold limits per range), `analyseBalance`, `analysePeaks`, `analyseBass`), all with hand-authored limits and tested without a UI. The graphs only format their results.
- **Level independence (TonalAnalyzer):** each frame's band energies are divided by that frame's total before they are averaged, and frames are gated *relative* to a running mean power (`kRelativeGateDb`; `kSilenceDb` only catches digital silence). Don't reintroduce an absolute dBFS gate or energy-weighted averaging; `tonal_analyzer_is_independent_of_level` and the two tests after it guard this.
- **Mono fold (TonalAnalyzer):** `push()` also stores the side signal; each frame yields per-band mid and side power as shares of the frame's total (M+S), averaged like the tonal curve and published as `10 log10(M/(M+S))` (`readMonoFoldDb`, `hasMonoFoldData`). The silence/relative gates use the mean of L and R power (= M+S), not mid alone, so an out-of-phase signal is still measured; `hasData()` (tonal curve) stays false for a pure-side signal while `hasMonoFoldData()` does not.
- **Shared analysis grid:** `BandGrid` in TonalAnalyzer.h (61 bands, 1/6-octave from 20 Hz) is the common representation for the analyzer and `TargetCurve` (built-ins, `fromTracks`, JSON `.themiscurve`). Curves are normalised to 0 dB mean over the 200 Hz–5 kHz anchor region (`normaliseAnchor`), so they express shape, not level.
- Cross-thread: the audio thread only calls `TonalAnalyzer::push` (lock-free ring, no FFT). A plugin-owned worker thread (`ThemisProcessor::AnalysisThread`, started in `prepareToPlay`, stopped in `releaseResources`/destructor) calls `pump()` every ~15 ms to run the FFT and publish through atomics. `requestReset` is applied by the next `pump`. `process()` = `push` + `pump` for offline/tests; `prepare()` must never overlap with `push`/`pump`. `FFT.h` has a complex `FFT` and a `RealFFT` (half-size complex FFT) used by the analyzer. `push()` also runs the clip meter (above). `LowCrestMeter` (and likewise `LoudnessMonitor` and, last of all, `Audition`) is the exception to "nothing but `push` on the audio thread": `processBlock` calls its `process()` directly (3 biquads/sample, no FFT, atomics out); `requestReset` is applied by the next `process()`, and `hasData()` already reports false while a reset is pending.

**`plugin/Source/` — JUCE layer**
- [Parameters.cpp/.h](plugin/Source/Parameters.cpp): five APVTS parameters (`target`, `tolerance`, `avgTime`, `device`, `loudnessTarget`; `device` = "Off" + the `DeviceProfile::builtIns()` names, so reordering those shifts saved sessions like the targets do); `params::Reader` caches the raw atomics.
- [PluginProcessor.cpp](plugin/Source/PluginProcessor.cpp): `processBlock` only *reads* the buffer into one `TonalAnalyzer` (via `push`) and one `LowCrestMeter` (never writes it; latency stays 0). State = APVTS XML plus a `customCurve` property holding the target curve as JSON. "Learn from tracks" decodes files on a lazily-created `ThreadPool` job with an `alive` shared flag guarding the async callback against processor destruction. Keep the constructor and `prepareToPlay` light: FL Studio instantiates the plugin while scanning.
- Editor (`PluginEditor` (header rows; right column = `AdvicePanel` over `StereoScopeView` + `AuditionPanel`; the plan refreshes every `kPlanRefreshTicks` timer ticks), `AdvicePanel.h`, `AuditionPanel.h`, `TonalBalanceView`, `HistoryViews.h` (`LevelView`/`FundamentalView` over a shared tabbed `HistoryPanel`: each `Tab` is data (series, axis, shaded zones, verdict function, tooltip), the panel draws the tab row, range chips, clickable legend, verdict line and plot; a new graph is a new `Tab`), `ThemisLookAndFeel`) is timer-driven and reads from the processor/atomics; it holds no DSP state.
- Built-in target names populate the `target` choice parameter, with "Custom" appended as the last index; reordering/adding built-ins in `TargetCurve::builtIns()` shifts that index and affects saved sessions.

**Tests**
- [tests/test_main.cpp](tests/test_main.cpp): DSP-only, no JUCE; covers the core library (loudness, limiter/compressor, EQ fit, curve JSON round-trip, engine…), including DSP no longer used by the plugin.
- [tests/plugin_smoke.cpp](tests/plugin_smoke.cpp): also checks Solo / Mute through `processBlock` (silent side of a mono signal, ignored under `setNonRealtime`, bit-exact after release) and prints the master plan of the demo programme. Includes the plugin sources directly (the `ThemisSmoke` target recompiles `Parameters/PluginProcessor/PluginEditor.cpp`), so new plugin `.cpp` files must be added to **both** `Themis` and `ThemisSmoke` in [CMakeLists.txt](CMakeLists.txt).

## Gotchas

- JUCE is AGPLv3/commercial; distributing builds has licensing implications (README, "Known limitations").
- The README documents known limiter overshoot on full-band white noise (up to ~1 dB); don't "fix" core tests by loosening ceilings without checking that note.
- Stereo in/stereo out only; `isBusesLayoutSupported` rejects everything else.
